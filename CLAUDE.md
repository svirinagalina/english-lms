# Advent Academy LMS

Galina's English-teaching platform. Production: **https://lms.advent-academy.online**, on server `srv3.advent-academy.online` (91.239.6.107), root SSH via `~/.ssh/lms_deploy`. Everything runs in Docker from `/opt/srv3/` (Caddy + app + Postgres). Repo: `svirinagalina/english-lms` (private, push over SSH).

## Stack
- `client/`: React 18 + Vite, plain CSS (`styles.css` + `styles/whiteboard.css`), React Router.
- `server/`: Node/Express (ESM), Prisma/PostgreSQL, Socket.io for the whiteboard and calls.
- Deploy: `git push` then `./deploy/deploy.sh` (builds, runs prisma migrate deploy, restarts the container, health-checks). Always commit with `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` (or the model name the session shows).

## Local dev
- `psql english_lms` for the local Postgres DB (same schema as prod, different data).
- Client dev server: `npx vite --port 5199` inside `client/`. Server: `node --env-file=.env src/index.js` inside `server/` — **does not hot-reload**; restart it after any server-side edit before testing, or you'll silently test stale code (this has bitten me more than once this session).
- Test accounts locally: `galina@test.com` / `localtest` (OWNER), `petr1789323310144@test.com` / `localtest` (STUDENT), others under `*@test.com`.
- Browser-pane camera/mic is blocked in this environment; mock `navigator.mediaDevices.getUserMedia` via `javascript_tool` before testing call/board flows (see call pages for the pattern used throughout this project).

## Working on production data safely
Never ask the user to paste `DATABASE_URL` or any credential into chat. I already have SSH access; either:
- run SQL via `docker exec srv3-lms-db psql -U $(docker exec srv3-lms-db printenv POSTGRES_USER) -d $(docker exec srv3-lms-db printenv POSTGRES_DB) -f /tmp/x.sql` after `scp`-ing the file up, or
- for a script that needs Prisma, `docker cp` it into `srv3-lms-app:/app/scripts/` and `docker exec -w /app srv3-lms-app node scripts/<name>.js` — `DATABASE_URL` is already set correctly inside that container.
Read logs with `docker logs --since 1h srv3-lms-app | grep '\[diag\]'` for call diagnostics (see below).

## Architecture notes (read before touching these areas)

**Boards, one per student (redesigned 2026-09-20/21).** A student's cabinet shows exactly one board, given to them via **Assign** (a checklist of students on any board in "My boards" — checking a name attaches this board and detaches whatever that student had before, moving the old one back to the teacher's own shelf, never deleting it; a board can be checked for several students at once for pair/group lessons). There is no "Extra board" button anymore — `POST /classrooms/:id/boards` refuses to create a board directly in a student's classroom. `home` for a displaced board must be `ensurePersonalSpace(target.teacherId, ...)`, **not** the acting user's — I shipped a bug where an admin managing another teacher's student sent the displaced board to the admin's own shelf; fixed, but if you touch `assign` again, re-check this. A `Board.scratch` flag marks boards auto-created for a "call without a student" (colleague/group call); they're excluded from every board listing and deleted when that call ends (`signaling.js`, the 15-min-after-empty cleanup).

A board shared into a student (the normal post-Assign state: owned by the teacher's shelf, shared into the student via `sharedWith`) legitimately belongs to *two* classroom contexts at once. `GET /classrooms/boards` (`classrooms.js`) used to dedup its result globally by board id, so whichever classroom Prisma iterated first "won" and the other context's row vanished entirely — if the shelf's row won, the student's own call could never find the board (`Call.jsx`'s `boards.find(b => b.classroomId === call.classroomId)` came up empty: board doesn't display, no cursor/spotlight sync since the two sides end up on different boards, and vocabulary/mistakes misattributed). Fixed 2026-09-21: the endpoint now emits one row per (board, classroom) pair; `Controls.jsx`'s board picker dedupes by id for display, and `Call.jsx`'s `currentBoard` lookup prefers the row matching the call's classroom, then any row naming the board's actual student, before an unattributed one. Also closed the race that produced a literal duplicate `<name> — lessons` board: `GET /classrooms/:id`'s check-then-create and `assign`'s board moves now run under a `pg_advisory_xact_lock` keyed by the target classroom id.

**OCR on board images (2026-09-21).** Words inside a pasted screenshot or photo now get the same hover-translate/pronunciation and add-to-vocabulary treatment as real text — `wordUnderImagePoint` (`Whiteboard.jsx`) maps a point through the image's crop into its natural pixel space and looks it up in that image's `ocrWords()` result (`client/src/utils/ocr.js`, Tesseract.js). Recognition is cached per image `src` and starts on first hover — the first touch of a new image has a beat of latency, everything after is instant. Self-hosted under `public/tesseract` (`worker.min.js` + `core/` gitignored and rebuilt by `scripts/copy-tesseract.js` on every `prebuild`, matching how `@mediapipe/tasks-vision` is handled for blur; only `lang-data/eng.traineddata.gz` is committed, since there's no npm package to regenerate it from). A teacher's double-click on an image still opens crop mode as before — the OCR word-card only intercepts it for `wordPicker` (student) mode, and only when there's actually a word under the point.

**Pronunciation audio is the browser's speech synthesis, not the server's clip (2026-09-21).** `PlayButton` (`WordCard.jsx`) calls `speakAmerican` (`utils/speech.js`) first, which asks for a voice tagged exactly `en-US`; only falls back to the server's `/api/dictionary/audio` clip if the browser has no en-US voice at all. Reason: `dictionary.js`'s `translate_tts` call turned out to return byte-identical audio regardless of `tl` or which Google domain (`.com` vs `.co.uk`) it's requested from — verified by diffing the responses — so there was no way to make that endpoint specifically American. Don't try tweaking its `tl`/domain again for this; it doesn't respond to either. The IPA transcription (separate from the audio) was already American-first on both its sources and didn't need this.

**Spotlight follows, but doesn't fight a follower's own panning (2026-09-21).** `board:view` arrives up to 10/s while someone spotlights, and used to be applied unconditionally on every receiving client — a follower panning or zooming on their own board got snapped back within ~100ms, which is what "the board won't move" during a lesson turned out to be. `followPausedRef` (`Whiteboard.jsx`) now stops applying incoming `board:view` the moment a follower pans/zooms/pinches themselves (`pauseFollowing()`, called from every manual-navigation path — drag-pan, `zoomAround`, `movePinch`, the wheel handler's pan branch); a fresh `board:spotlight {on:true}` resets it, so the teacher can still pull everyone back to one place on demand. If you add a new way to move the view, call `pauseFollowing()` from it too or it'll silently be exempt from this. (`glideTo()` — New lesson/Homework's jump to the new heading — no longer animates at all, so it can't fight a manual pan the way it briefly could; see below.)

**`addHeading` (New lesson/Homework) doesn't move the view at all (2026-09-21).** First it animated there, then it jumped instantly, and Galina still called that "flying away" — the person clicking is already on the board, so any view change displaces them from whatever they were doing. It just adds the element now; nothing calls `glideTo` from that path any more. `glideTo` itself (instant, no animation — that part came first) still exists for `addBlock`, the one caller where a jump is actually correct: inserting a lesson summary's speaking questions from *outside* the board, where the person isn't already looking at it and does need the new content brought into view.

**`render()`'s per-element draw is wrapped in try/catch (2026-09-21).** Reported live as "the board disappears until reload" after New lesson/Homework — never reproduced under those exact steps, but the underlying risk was real and is now closed regardless: the draw loop over `elementsRef.current` had no error handling, so one element throwing (a stray NaN coordinate, a crop that no longer matches its image, a canvas hitting a browser's size limit at extreme zoom+pan on a huge image) left the canvas cleared for that frame and every one after — permanent until a reload got one fresh mount, and even then only until the same bad data threw again. Now each element's own try/catch logs and skips it instead. If this ever gets reported again, the browser console (`Failed to draw board element ...`) will name the element id/type responsible — check that first rather than re-guessing at reproduction steps.

**Writing: a reconnect used to overwrite unsent local text (fixed 2026-09-21).** Reported live as "I wrote something and it disappeared." `Writing.jsx`'s `doc:open` ack ran on every reconnect (a deploy dropping the socket, or an ordinary network blip) and unconditionally did `setRuns(response.runs)` — the server's last-known copy — with no check for newer, unconfirmed text already sitting in the editor; anything typed while briefly offline was silently discarded the instant the connection came back. `dirtyRef` now marks local edits since the last settled sync, and a reconnect (`quiet` reopen) with it still set keeps the local runs and rebroadcasts them instead of accepting the server's — verified by disconnecting the socket mid-session, typing offline, reconnecting, and confirming the text both stayed on screen and reached the database. This class of bug (socket drop → blind server-wins resync) is worth checking for in any other place that does a `doc:open`/`board:open`-style full-state resync on reconnect — `Whiteboard.jsx`'s own `board:open` reconnect does the same unconditional overwrite (`elementsRef.current = dedupe(response?.elements ?? [])`) and hasn't been given the same treatment yet; lower urgency since board edits go over the wire per-element rather than as one full-document blob, but the same failure mode is there if it's ever reported.

**Writing: headings, highlighter, autocorrect, area screenshot (2026-09-25).** Runs can carry `h` (heading line → listed in the left "Contents" outline, click jumps there) and `hl` (highlighter colour); neither is a tracked suggestion, both must stay in `runSchema` (`docStore.js`) or zod silently strips them. Typed text inherits `h`/`hl` from its neighbour (`inheritedStyle`); `resolveAll/One` keep formatting via `asBase`. A teacher-deleted line break renders as a struck `↵` (same length, offsets stay honest) — before, it kept breaking the line, so a blank line the teacher deleted never visually went away and Backspace kept re-striking the same char; `skipStruck` now steps over struck text. Images are `inline-block; width:100%`, not `block` — as a block, the `\n` after an image rendered as a phantom blank line. A `<br>` sentinel follows a trailing `\n` (otherwise Enter at the very end did nothing visible and the next text landed before the break). Tools that steal focus (file dialog, screen picker) insert at `lastSelRef`, the last caret seen via `selectionchange`. Autocorrect (`utils/autocorrect.js`) defaults on for staff, off for students (their mistakes are the exercise), per browser in localStorage; it only touches the actor's own text and is a separate undo step. Screenshot = `RegionCapture.jsx` (getDisplayMedia → one frame → drag a rectangle); tested locally with a mocked canvas stream, the real OS picker not exercised.

**Phone board = no toolbars, finger-only (2026-09-25).** `phone = useNarrow() && isMobile()` in `Whiteboard.jsx` (so a narrow *desktop* window keeps its tools). On a phone the dock, corner undo/zoom, text toolbar and name chip are not rendered — only a small Back pill (`.board-back-phone`); `--dock-h` is set to 0 so the call controls drop to the bottom edge. Input is a `tap` pointer mode decided on lift/travel: tap on text/note → edit at that point; tap on empty → new text; drag (>8px) on an element → move it (staff only — students still never rearrange the board, their drag pans); drag on empty → pan; two fingers → the existing pinch zoom (`trackTouch` cancels the pending tap). Double tap (<320 ms, <30 px) = double-click: a student's word card, a teacher's crop; a student's single tap on text waits 300 ms so a double tap can cancel the editor. `onTouchEnd` on the canvas re-focuses a just-opened editor because iOS only raises the keyboard for a focus made inside a touch handler — **not verified on a real iPhone** (only in the Android-emulated browser pane). No selection handles are left behind on a phone after a move or an edit.

**New lesson / Homework headings and Mistake notes land at the *work spot* (2026-09-25, supersedes the two 09-21 notes below).** Both were still reported as landing "too far from the cursor": headings went under everything on the board (far off screen on a long board), and mistake notes used the raw last pointer position — which the trip down to the dock / over to the Mistakes panel had already dragged to the screen's edge. `workSpotRef` (`Whiteboard.jsx`) is the last pointerdown on the canvas, or where the pointer rested ≥500 ms (`dwellTimerRef`; cleared on pointerleave so a quick crossing doesn't count); `workSpot()` falls back to the upper-left quarter of the view if that spot has scrolled off screen. A new heading is placed there and selected so it can be dragged. `addBlock` (lesson-summary questions, inserted from outside the board) still goes under everything via `addHeading(..., { below: true })`.

**Mistake notes land at the teacher's cursor, not a fixed spot (2026-09-21).** Was anchored to `rect.width - 720` regardless of what was actually being discussed. `lastCursorWorldRef` (`Whiteboard.jsx`) tracks the pointer's last world position on every move over the canvas; a saved mistake (or several in one submission) now lands there instead, stacking downward within that one submission same as before — falls back to the old fixed spot only if the pointer never touched the canvas this session.

**Vocabulary/mistakes: the "which student?" prompt now reflects the board's actual assignees, not the whole roster (2026-09-21).** `Call.jsx`'s `boardAssignees` derives from every row `/classrooms/boards` returns for this exact `boardId` that has a `studentId` — shared with exactly one student → no prompt, straight to them; several (pair/group lesson) → prompt with just those; none (real teacher's-own material) → prompt with the whole roster, as before. Also: `boards` is now refetched on every call reconnect, not just once at mount — root cause of the bug report was a board shared to a student *after* the call tab's initial load, which a mid-call deploy-triggered reconnect never picked up, so the board still read as ownerless material. If a similar "board looks unassigned when it shouldn't" report comes up again, suspect stale `boards` state before re-diagnosing the assignment logic itself. **The same fix was needed a second time in `Classroom.jsx`** (opening your own board straight from "My boards", not through a call) — its `students`/`myStudents` had the identical "whole roster regardless of this board's actual sharing" bug; fixed the same way via `openBoard.sharedWith` (that field already carries the exact assignee list, no extra fetch needed). If this class of bug gets fixed again somewhere, check both files — they duplicate this logic rather than sharing it.

**A mistake's correct form is optional (2026-09-21).** `mistakes.js`'s schema and `Whiteboard.jsx`'s Mistakes panel used to both require it (`correct: z.string().min(1)` server-side; the submit button's own `disabled` condition client-side, independent of the row filter — when adding "just the error" ask, I fixed the filter and missed that the button had its own separate, stricter check, so nothing happened on click until I actually tested it locally and found `btn.disabled === true`; test the actual button state, not just the handler's logic, when validation changes). Now only `said` is required; a note with no correction reads "(no correction yet)" instead of a blank `✓` line, and `MistakeNotebook.jsx` shows a "+ add the correct form" link (opens the existing edit form) in its place. Classification (`topicsFor`) and the drill prompt (`promptFor`) both skip a mistake with no correction — nothing to diff or translate against yet — and `GET /practice` excludes them from drilling for the same reason.

**The "For [student]" switcher lives on the board's name chip, not inside Mistakes (2026-09-22).** Vocabulary and Mistakes share one `target` (who a save currently goes to) by design, but only Mistakes' panel had a control for it — switching who vocabulary words went to meant opening Mistakes just to touch its picker, then closing it again. That `<select>` moved to `board-chip` itself (`Whiteboard.jsx`, `.mistakes-target` reused with a compact variant in `whiteboard.css`), visible whenever the board has more than one assignee (`students?.length > 1`); Mistakes now just shows who it's currently set to, in plain text. Verified: switching there redirects the very next +Vocabulary add immediately.

**A lesson summary's "Put questions on the board" silently did nothing for most students (fixed 2026-09-22, found in a broad sweep, not reported).** The link passes `?board=default`; `Classroom.jsx` resolved that to `classroom.boards.find(b => !b.shared)` — "the board this classroom owns outright" — which broke the moment the Assign redesign made a student's one board *normally* a shared one (owned by the teacher's shelf, shared into the student). A student's classroom only ever has exactly one board now regardless of owned/shared, so `default` is just `classroom.boards[0]`. No error anywhere — the link just quietly did nothing, so this class of bug (a board-identity assumption from before the one-board-per-student redesign) is worth grepping for again (`grep -rn "!.*\.shared\b"`) if something similar turns up.

**Font size silently not applying while editing text (fixed 2026-09-22).** Clicking the size `<select>` in the text toolbar while actively typing opens a *native* dropdown, which blurs the contentEditable immediately — before the select's `onChange` ever fires — via a browser-level focus change whose `relatedTarget` isn't reliably the select itself. The toolbar's existing blur guard only checked `relatedTarget`, missed this, and `submitText()` closed the editor out from under the still-in-progress pick; by the time `onChange` ran, `textInput` was already `null`, so the size change either went nowhere or landed on whatever ended up selected instead. `toolbarInteractingRef` (`Whiteboard.jsx`) is now set synchronously on the toolbar's own `mousedown` — strictly before that blur — and `onBlur` checks it alongside `relatedTarget`. Verified by replaying the exact sequence (mousedown then a `blur` with `relatedTarget: null`): the editor survives it and the size applies live. **If a similar "control X doesn't work while editing text" report comes up, suspect this same native-`<select>`-steals-focus mechanism first** — anything that opens an OS-level popup (a native select, but potentially a native color/date picker too) can blur the editor the same way.

**Paste dumping raw JSON into text (fixed 2026-09-22).** `copySelection()` (⌘C on a board element) overwrites the *system* clipboard with this board's own JSON copy format (`{"mark":"english-lms-board/v1","elements":[...]}`, `CLIPBOARD_MARK`) so elements round-trip between boards — reported live as pasting into a text box inserting that raw JSON instead of the word it was supposed to represent. The text editor's `onPaste` (separate from the board-level paste handler, which already understood `CLIPBOARD_MARK`) didn't check for it at all. It now recovers the actual words those elements held (markup stripped via `textRuns`, the same helper `selectedWords()` uses) instead of inserting the JSON verbatim.

**Noise suppression can silently fall back to the browser's own on some phones — known limitation, not fixed.** `buildDenoiser` (`noiseSuppressor.js`) requires the `AudioContext` to actually be running at 48000 Hz; `createContext()` already requests that rate explicitly, but some phones' hardware won't honor it (the constructor doesn't throw, `ctx.sampleRate` just ends up something else), which trips the sample-rate guard and throws, and the caller falls back to the raw mic. That mic still has the *browser's own* `noiseSuppression`/`echoCancellation` constraints applied (`AUDIO_CONSTRAINTS` in `Call.jsx`, requested unconditionally) — so it's "missing our extra neural layer," not "zero suppression" — but on an affected phone it does sound noticeably worse than desktop. A real fix means resampling the mic to 48kHz before the denoiser (a new pipeline stage) rather than requiring the context itself to run at that rate; flagged to Galina as a bigger, riskier change, not attempted blind.

**A student needing a VPN to connect is not a code bug — check DNS/Cloudflare first.** `lms.advent-academy.online` resolves to Cloudflare's edge IPs (`188.114.x.x`), not the origin server directly (confirmed via `dig`) — Cloudflare's IP ranges get regionally blocked/throttled in various countries independent of anything this app does, and "works with a VPN, not without" is the classic signature of that, not an app-level failure (nothing in server logs when it happens — the request never arrives). Her partner controls the Cloudflare account and DNS (see "Where it lives" above); the fix, if confirmed, is switching that DNS record to "DNS only" (grey cloud) so it resolves straight to the origin's real IP, not a code change here.

**Pronunciation excludes novelty system voices (2026-09-21).** `getAmericanVoice` (`utils/speech.js`) picked the first `en-US` voice with no regard for which one; on a student's machine that turned out to be one of macOS's built-in "novelty" voices (Bahh, Zarvox, Albert, Wobble, …) — reported as sounding like someone gasping for air. Now excludes those by name (`NOVELTY_VOICES`) and prefers a short list of known-good ones (Samantha, Google US English, Microsoft's "Natural" voices, …) when more than one option exists.

**Per-word font size is not supported (noted 2026-09-21, not fixed).** Reported as "font size doesn't work when I select one word" — `fontSize` is a whole-element property (`setFontSize` in `Whiteboard.jsx`), unlike bold/italic/color which are markup spans within a text's runs (see `textRuns`/`COLOR_OPEN` near the top of the file) and so can apply to just a selection. Making font size selection-aware would mean adding a size span to that markup and threading it through layout (`textLines`), measurement (`measureWidth`), and rendering — a real feature, not a bug fix. Don't build it without asking first; flagged to Galina, no decision yet.

**Noise removal and blur (`client/src/utils/noiseSuppressor.js`, `videoProcessor.js`).** Chain: browser filter → GTCRN neural denoiser (RNNoise fallback) → a custom "quiet-gate" AudioWorklet (−48/−54 dBFS) that was the fix that actually mattered — GTCRN alone left audible residue. Both sender and receiver denoise (VideoGrid denoises incoming audio too). Never awaited at join (plain mic first, swapped in when ready). Blur: mediapipe selfie segmenter; iPhone/iPad force the CPU delegate and the frame is copied to a canvas before compositing (Safari ignores `globalCompositeOperation` on a `<video>` source) — both were real bugs found via the `/api/diag` log, not guesswork. **Diagnostics are the fastest way to debug a "doesn't work for the student" report**: the browser POSTs to `/api/diag`, read with `docker logs ... | grep '\[diag\]'`; `blur.mask` events even carry a base64 thumbnail of what was actually composited. Trust this over guessing, and over the user's own uncertain description of what's wrong — but *do* trust the user's plain sensory report ("I can still hear the fan") over my own instrumentation if they conflict; that once turned out to mean the instrumentation was reading the wrong signal, not that the user was wrong.

**Practice answers the key doesn't cover go to the AI (2026-09-25).** `POST /units/exercises/:id/attempt` still runs `checkAnswer` first (free, instant); only a miss on a TRANSLATE/FILL_BLANK exercise goes to `judgeExerciseAnswer` (`assistant.js`) — chapter title + task + key + answer, accepts any correct variant, returns one Russian sentence of feedback shown under the verdict (`UnitPractice.jsx`; "In the book: …" when the AI accepted a different wording). Verdicts are cached in memory per (exercise, normalised answer); a 20 s timeout falls back to the rule verdict. The provider is whatever `aiConfig()` picks — on prod that's OpenAI (`OPENAI_API_KEY` in the env *and* a key saved in Settings; env wins). **GPT-5.x is a reasoning model: a small `maxTokens` (the old 50–300 caps) can be eaten by its thinking and `output_parsed` comes back null** — that silently broke some judge calls; every short call now has ≥1000 tokens and `effort: 'low'` (new `structured()` option, OpenAI only).

**Exercise grading (`server/src/answerCheck.js`).** `checkAnswer()` is shared by grammar-unit exercises (`units.js`) and the mistake-notebook drill (`mistakes.js`) — a fix here covers both. Fixed 2026-09-21: a "no article needed" exercise stores its answer as an em dash `—`, which normalises to an empty string; the code used to reject any empty-normalised answer outright before comparing, so no student input could ever match. Lone `-`/`_` now normalise the same way `—` does (only when they stand alone as a "word" — `well-known` is untouched), and the empty-vs-empty case is judged like any other instead of short-circuited.

**Calls started from a board reach its students (2026-09-26).** Reported: a student (Anna) had no "Join call" in her cabinet and could only join by link. **Phone sound & blur, round 2 (2026-09-26).** Reported: students on phones sound worse; blur on iPhone lags and looks odd. No phone diag had survived (see the persistent diag file), so these are fixes by reasoning, verify with the file after the next phone lesson. (1) Sound was denoised twice — on the sender and again on every receiver (`PeerVideo`) — and a phone ran two neural denoisers at once (its mic + the teacher's incoming voice). **Idle calls are swept (2026-09-26).** The only thing that ended a call used to be the in-memory 15-minute timer on the last person's exit — lost on every deploy/restart, and never started for a call nobody entered — so 68 calls had piled up open (closed by hand on prod). `sweepCalls` in `signaling.js` now runs 1 min after start and every 5 min: a call whose room is empty is ended 15 min after someone was last in it (`callLastSeen`, updated on join/leave), 60 min after creation/server start if nobody was seen, or at once if unseen and over 3 h old; scratch boards older than 24 h that aren't open in a room are deleted.
