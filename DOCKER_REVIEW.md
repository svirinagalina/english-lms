# Обзор Dockerfile Advent Academy LMS

Дата проверки: 9 октября 2026 года.

Проверяемый файл: `server/Dockerfile`.

## Общая оценка

Dockerfile рабочий, но скорее представляет собой прагматичный production MVP, чем полностью воспроизводимый и укреплённый production-образ.

## Что сделано хорошо

- Используется Node.js 22, который нужен проекту.
- Alpine делает базовый образ относительно компактным.
- `npm ci`, а не `npm install`, обеспечивает установку по lock-файлу.
- Сначала копируются `package.json` и `package-lock.json`, поэтому Docker может кешировать слой с зависимостями.
- Prisma Client генерируется во время сборки.
- Перед запуском приложения выполняются миграции.
- `exec node` корректно передаёт Node.js сигналы остановки, поэтому graceful shutdown приложения работает.
- Секреты явно не копируются в образ и ожидаются через environment variables.

## Что стоит исправить

### 1. Контейнер работает от `root`

В Dockerfile нет директивы `USER node`. Если в приложении появится RCE, атакующий получит root внутри контейнера.

Рекомендация: запускать приложение от встроенного пользователя `node`, предварительно выдавая ему права на рабочий каталог и upload-volume.

### 2. Prisma CLI и `--omit=dev` конфликтуют концептуально

Устанавливаются только production-зависимости:

```dockerfile
RUN npm ci --omit=dev
```

Но пакет `prisma` объявлен в `devDependencies`, после чего Dockerfile вызывает:

```dockerfile
RUN npx prisma generate
CMD ["sh", "-c", "npx prisma migrate deploy && exec node src/index.js"]
```

Lock-файл помечает Prisma как `devOptional`, поэтому фактическое наличие CLI зависит от разрешения optional peer dependency конкретной версией npm. В худшем случае `npx` попытается скачать CLI во время сборки или старта контейнера.

Контейнер не должен зависеть от npm registry при запуске.

Возможные решения:

- перенести `prisma` в `dependencies`, если миграции остаются в `CMD`;
- либо выполнять миграции отдельным deploy-job;
- вызывать `./node_modules/.bin/prisma`, а не `npx prisma`.

### 3. Сборка не самодостаточна

Dockerfile выполняет:

```dockerfile
COPY public ./public
```

Но в чистом checkout каталог `server/public` отсутствует. Его перед production-сборкой создаёт `deploy/deploy.sh`, предварительно собирая React и копируя `client/dist` на сервер.

Поэтому обычная команда:

```bash
docker build server
```

из чистого checkout не соберёт образ. Результат зависит от неочевидного порядка действий deploy-скрипта.

Рекомендации:

- собирать клиент внутри multi-stage Dockerfile;
- либо явно передавать готовый frontend-артефакт и документировать это как обязательный шаг.

### 4. Нет `.dockerignore`

Build context потенциально может включать:

- `.env`;
- `node_modules`;
- uploads;
- отчёты;
- временные файлы;
- локальные логи.

Даже если они не попадают в слои через `COPY`, они передаются Docker daemon и могут оказаться в build cache.

Минимальный `server/.dockerignore`:

```dockerignore
node_modules
.env
.env.*
uploads
reports
npm-debug.log*
.git
```

### 5. Миграции выполняются при каждом старте

```dockerfile
CMD ["sh", "-c", "npx prisma migrate deploy && exec node src/index.js"]
```

Для одного экземпляра это допустимо. Но при масштабировании несколько контейнеров одновременно запустят миграции. Кроме того, ошибка БД или миграции не позволит приложению стартовать.

Рекомендация: запускать `prisma migrate deploy` отдельным одноразовым шагом перед обновлением приложения.

### 6. Базовый образ не закреплён

```dockerfile
FROM node:22-alpine
```

Сегодня и через месяц этот тег может содержать разные версии Node.js, Alpine и системных пакетов.

Лучше закрепить хотя бы patch-версию, а для строгой воспроизводимости — digest:

```dockerfile
FROM node:22.20.0-alpine@sha256:...
```

Digest необходимо обновлять контролируемо вместе с security patches.

### 7. Нет container healthcheck

У приложения есть endpoint `/api/health`, но Dockerfile его не использует. Сейчас проверка выполняется только после deploy.

Возможный вариант:

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
  CMD wget -qO- http://127.0.0.1:4010/api/health >/dev/null || exit 1
```

Если healthcheck уже задан в production Compose, дублировать его в Dockerfile необязательно.

### 8. Несовпадение порта требует проверки

Dockerfile объявляет:

```dockerfile
EXPOSE 4010
```

Сервер по умолчанию слушает порт `4000`:

```js
const port = process.env.PORT ?? 4000
```

Вероятно, production Compose задаёт `PORT=4010`, но Dockerfile сам по себе этого не отражает.

Рекомендация: явно добавить `ENV PORT=4010` либо согласовать `EXPOSE` со значением по умолчанию.

### 9. В runtime копируются административные скрипты

```dockerfile
COPY scripts ./scripts
COPY data ./data
```

Если они не нужны работающему приложению, лучше не включать их в runtime-образ. В каталогах находятся скрипты импорта, исправления и генерации контента. При компрометации процесса это лишний доступный инструментарий и дополнительная поверхность образа.

### 10. Нет автоматической проверки уязвимостей образа

В текущей цепочке сборки не видно запуска:

- `npm audit`;
- Trivy;
- Grype;
- Docker Scout;
- SBOM-генерации.

Ранее `npm audit --omit=dev` для сервера показал уязвимости вплоть до critical, поэтому проверку зависимостей желательно сделать обязательной частью CI.

## Рекомендуемый порядок исправления

1. Добавить `server/.dockerignore`.
2. Убрать неопределённое использование Prisma CLI через `npx`.
3. Перевести runtime на пользователя `node`.
4. Сделать сборку самодостаточной или формально определить frontend artifact как вход сборки.
5. Согласовать `PORT` и `EXPOSE`.
6. Добавить Docker/Compose healthcheck.
7. Вынести миграцию в отдельный deploy-step.
8. Убрать из runtime ненужные scripts/data.
9. Закрепить версию базового образа и настроить контролируемые обновления.
10. Добавить сканирование зависимостей и контейнерного образа в CI.

## Итог

Dockerfile способен запустить production, но имеет четыре главных архитектурных долга:

1. запуск от root;
2. неясная установка Prisma CLI;
3. зависимость от заранее созданного `server/public`;
4. отсутствие `.dockerignore`.

Для этого проекта не нужны микросервисы или Kubernetes. Достаточно сделать воспроизводимый multi-stage build, запускать контейнер от непривилегированного пользователя, отделить миграции и добавить healthcheck.
