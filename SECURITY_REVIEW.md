# Security review Advent Academy LMS

Дата проверки: 9 октября 2026 года.

## Область проверки

Это статический аудит текущего кода приложения. Проверялись:

- аутентификация и роли;
- разграничение доступа REST и Socket.IO;
- CSRF и браузерные защиты;
- загрузка и раздача файлов;
- хранение секретов;
- Stripe webhooks;
- зависимости `server`, `client` и `mobile`.

Конфигурация production Caddy, firewall, Docker-сети и реальные права файлов в эту проверку не входили.

## Общая оценка

Фундамент безопасности неплохой, но обнаружено несколько серьёзных проблем. До их исправления приложение не стоит считать безопасным для хранения учебных материалов и персональных данных.

Главный риск связан не с криптографией или SQL injection, а с авторизацией и публичной раздачей файлов.

## Критичные проблемы

### P1: `PARTNER` фактически получает права владельца

В Prisma роль описана как доступ только к Content:

```prisma
// Works on the school's marketing content; sees only the Content section.
PARTNER
```

Файл: `server/prisma/schema.prisma`.

Но проверка ролей в `server/src/auth.js` автоматически считает `PARTNER` владельцем:

```js
export const isAdmin = (user) => user.role === 'OWNER' || user.role === 'PARTNER'

export function requireRole(...roles) {
  return (req, res, next) => {
    const allowed = roles.includes(req.user.role) ||
      (roles.includes('OWNER') && req.user.role === 'PARTNER')
    if (!allowed) return res.status(403).json({ error: 'Not allowed' })
    next()
  }
}
```

В результате партнёр прямым API-запросом может получить доступ к маршрутам, визуально скрытым в UI:

- менять AI-, Stripe-, Advent- и LiveKit-настройки;
- загружать APNs private key;
- управлять подписками;
- удалять преподавателей и студентов;
- читать кабинеты, платежи и активность школы.

Это нарушение принципа минимальных привилегий и реальная вертикальная эскалация.

Рекомендация: `requireRole('OWNER')` должен означать только `OWNER`. Для совместного доступа необходимо явно писать `requireRole('OWNER', 'PARTNER')`.

### P1: диагностические логи доступны как публичные файлы

Диагностика записывается в:

```text
UPLOAD_DIR/diag/diag-YYYY-MM.log
```

Код: `server/src/routes/diag.js`.

Весь `UPLOAD_DIR`, кроме учебников, раздаётся без авторизации:

```js
app.use('/uploads/textbooks', (req, res) => res.status(404).end())
app.use('/uploads', express.static(uploadDir, { maxAge: '30d', immutable: true }))
```

Код: `server/src/index.js`.

Следовательно, потенциально доступен предсказуемый адрес:

```text
/uploads/diag/diag-2026-10.log
```

Логи содержат имена, роли, идентификаторы звонков, сведения об устройствах и диагностические сообщения.

Рекомендации:

- хранить diagnostics вне публичного upload-каталога;
- запретить `/uploads/diag` на уровне Express и reverse proxy;
- проверить, не доступны ли уже созданные файлы на production;
- после закрытия доступа оценить необходимость удаления старых логов.

### P1/P2: Socket.IO доверяет клиенту право менять чужой контент

После открытия разрешённой доски пользователь может отправить произвольные события:

- `board:update`;
- `board:delete`;
- `doc:update`.

Сервер проверяет структуру сообщения, но не проверяет автора элемента при update/delete. Код находится в `server/src/signaling.js`.

UI может разрешать студенту удалять только собственные элементы, но пользователь способен вызвать Socket.IO event вручную и:

- изменить или удалить текст преподавателя;
- удалить домашнее задание;
- переписать весь Writing-документ;
- подделать `author` у Writing runs;
- убрать исправления преподавателя.

Рекомендации:

- проверять разрешение каждой операции на сервере;
- студент должен менять только собственные элементы доски;
- не принимать `authorId` и `author` как доверенные значения клиента;
- для Writing передавать ограниченные операции, а не принимать целиком новый документ;
- добавить security-тесты на Socket.IO permissions.

### P1/P2: возможен stored XSS через Content uploads

Content API проверяет заявленный `Content-Type`, но сохраняет расширение исходного имени:

```js
const mime = req.get('content-type')
const stored = `${randomBytes(6).toString('hex')}-${name}`
```

Код: `server/src/routes/content.js`.

Можно отправить:

```http
Content-Type: text/plain
X-File-Name: payload.html
```

Файл сохранится с `.html`, после чего `express.static` может отдать его как HTML на основном домене. При открытии такой ссылки JavaScript выполняется в origin LMS и получает возможность отправлять запросы с cookie пользователя.

Рекомендации:

- расширение файла должно определяться сервером из проверенного MIME;
- загружаемые документы отдавать с `Content-Disposition: attachment`;
- установить `X-Content-Type-Options: nosniff`;
- проверять сигнатуры файлов, а не только заголовок;
- в идеале раздавать uploads с отдельного cookieless-домена;
- запретить активные форматы HTML/SVG либо тщательно очищать их.

## Высокий приоритет

### Уязвимые зависимости

Команда `npm audit --omit=dev` показала:

- `server`: 1 critical, 3 high, 2 moderate;
- `client`: 2 moderate, 1 low;
- `mobile`: уязвимостей не найдено.

На сервере присутствует critical advisory в `proxy-addr`. Это важно, поскольку Express использует:

```js
app.set('trust proxy', 1)
```

а rate limiting зависит от `req.ip`.

Практическая применимость конкретной уязвимости при числовом trust mode требует отдельной проверки, но зависимость необходимо обновить. Также следует подтвердить, что Node-порт невозможно вызвать напрямую в обход Caddy.

На клиенте устарел `react-router-dom`; audit сообщает об open redirect и SSR hydration проблемах. SSR в проекте не используется, поэтому SSR-сценарий, вероятно, неприменим, но обновление всё равно требуется.

### Нет полноценной защиты от CSRF

Уже используются хорошие базовые меры:

- `HttpOnly`;
- `Secure` в production;
- `SameSite=Lax`;
- фиксированный CORS origin.

Однако нет CSRF-токена или проверки `Origin`/`Sec-Fetch-Site` на изменяющих запросах. `SameSite=Lax` защищает от большинства внешних сайтов, но не от потенциально недоверенного sibling-subdomain в пределах одного site.

Минимальная рекомендация: для `POST`, `PUT`, `PATCH`, `DELETE` проверять `Origin` против `CLIENT_ORIGIN`.

### Учебные изображения публичны по URL

Изображения досок, Writing и аватары сохраняются в `/uploads` и раздаются без авторизации. Случайные имена затрудняют подбор, но это не является контролем доступа.

При утечке URL через логи, скриншот, историю браузера или referer файл остаётся доступным без входа.

Рекомендация: использовать авторизованный download endpoint, подписанные короткоживущие URL либо отдельное приватное файловое хранилище.

## Остальные риски

- Rate limiting хранится в памяти одного процесса: после рестарта счётчики обнуляются, а при нескольких инстансах обходятся распределением запросов.
- Для Socket.IO ограничено число соединений, но нет строгих лимитов частоты событий доски и Writing.
- JWT действителен семь дней и не имеет session version. Смена пароля не отзывает уже украденный токен.
- Ключи шифруются AES-256-GCM, но ключ шифрования производится из `JWT_SECRET`. Компрометация одного секрета одновременно раскрывает настройки и позволяет подписывать JWT.
- В приложении не видно CSP, HSTS, frame protection и Permissions Policy. Часть заголовков может задаваться Caddy, но это не подтверждено кодом репозитория.
- Практически нет security-тестов на IDOR, роли и Socket.IO permissions.

## Что уже сделано хорошо

- Пароли хешируются bcrypt с cost 12.
- JWT находится в `HttpOnly` cookie.
- Роль пользователя перечитывается из БД на каждом запросе.
- Большинство запросов ограничено `schoolId`.
- Доступ к Classroom централизован через `accessibleClassroom`.
- API-токены хранятся только как SHA-256 hash.
- Stripe webhook проверяется HMAC через `timingSafeEqual` и имеет временное окно.
- Учебники не раздаются через публичный static route.
- Для входных данных широко используется Zod и ограничения размера.
- Внешние HTTP-вызовы имеют timeout, retry и circuit breaker.
- Есть rate limiting для login, signup, AI и API в целом.
- Секреты в базе зашифрованы AES-256-GCM.

## Рекомендуемый порядок исправления

1. Исправить семантику `requireRole('OWNER')` и провести аудит всех маршрутов для `PARTNER`.
2. Немедленно закрыть `/uploads/diag` и вынести диагностические логи из публичного каталога.
3. Ввести server-side permissions для изменения доски и Writing через Socket.IO.
4. Запретить активный HTML и несоответствие MIME/расширения в Content uploads.
5. Обновить уязвимые зависимости и повторить `npm audit`.
6. Добавить Origin/CSRF-защиту и security headers.
7. Закрыть учебные изображения авторизацией или подписанными URL.
8. Добавить автоматические тесты на роли, IDOR и realtime-операции.
